# Проектирование базовых мер безопасности

## 1. Аутентификация мобильного приложения

Для мобильного приложения предлагается использовать **OAuth 2.0 + OpenID Connect (OIDC)** с Authorization Code Flow и **PKCE**.

Такой подход позволяет не передавать пароль пользователя мобильному приложению и не хранить его в приложении. После успешной аутентификации Identity Provider выдаёт приложению `access_token` и `refresh_token`.

Для доступа к API используется только `access_token`, который передаётся в HTTP-заголовке:

Authorization: Bearer <access_token>
Токены должны иметь ограниченный срок действия. Access Token рекомендуется сделать короткоживущим, например 15 минут, а Refresh Token использовать для получения нового Access Token
```
Схема аутентификации
+-------------------+
|   Мобильное       |
|   приложение      |
+---------+---------+
          |
          | 1. Authorization Request
          |    + PKCE
          v
+-------------------+
| Identity Provider |
| OAuth 2.0 / OIDC  |
+---------+---------+
          |
          | 2. Authentication
          |    MFA при необходимости
          |
          | 3. Authorization Code
          v
+-------------------+
|   Mobile App      |
+---------+---------+
          |
          | 4. Code + PKCE Verifier
          v
+-------------------+
| Identity Provider |
+---------+---------+
          |
          | 5. Access Token
          |    Refresh Token
          v
+-------------------+
|   Mobile App      |
+---------+---------+
          |
          | 6. HTTPS
          | Authorization:
          | Bearer <access_token>
          v
+-------------------+
|    API Gateway    |
+---------+---------+
          |
          | 7. Validate JWT
          |    issuer / audience /
          |    signature / expiry
          v
+-------------------+
| IT-системы        |
| Здоровья+         |
+-------------------+
```
Дополнительные требования
API Gateway должен проверять:
- цифровую подпись JWT;
- iss — доверенный Identity Provider;
- aud — предназначение токена;
- exp — срок действия;
- scope / роли пользователя;
- sub — идентификатор пациента.
  
Для мобильного приложения следует использовать Authorization Code + PKCE, а не Implicit Flow.
Refresh Token должен храниться в защищённом хранилище ОС:
iOS — Keychain;
Android — Android Keystore / защищённое хранилище.

## 2. Rate Limiting
Rate Limiting необходимо реализовать на API Gateway. Лимиты должны учитывать как IP-адрес, так и идентификатор пользователя после аутентификации.
Для критической операции создания записи дополнительно необходимо использовать Idempotency-Key, поскольку одного Rate Limiting недостаточно для защиты от повторного создания записи.

| Тип запроса | Лимит | Действие при превышении |
|-------------|-------|--------------------------|
| **Публичный:** поиск врачей | 60 запросов в минуту на IP | HTTP 429 Too Many Requests, заголовок Retry-After; временное ограничение запросов с IP |
| **Авторизованный:** создание записи к врачу | 10 запросов в минуту на пользователя + 2 запроса в секунду | HTTP 429 Too Many Requests, Retry-After; запись не создаётся |
| Создание записи с одинаковым Idempotency-Key | Повторный запрос с тем же ключом не считается новой операцией | Вернуть результат первоначальной операции, не создавать новую запись |

Почему лимиты отличаются

Поиск врачей является публичным read-only запросом, поэтому допустим относительно высокий лимит. При этом он потенциально может использоваться для DDoS или автоматизированного массового сбора данных.

Создание записи — авторизованная бизнес-операция с изменением состояния системы. Поэтому лимит значительно ниже. Дополнительный ограничитель 2 RPS защищает сервис расписания от кратковременного burst-трафика.

Rate Limiting не должен заменять идемпотентность: пользователь может дважды нажать кнопку «Записаться», и оба запроса могут попасть в систему в пределах разрешённого лимита. Поэтому для POST /appointments обязательно использовать Idempotency-Key.

## 3. Защита каналов передачи данных

Все взаимодействия мобильного приложения с API Gateway должны выполняться исключительно по HTTPS с TLS 1.2+, предпочтительно TLS 1.3.

#### Обязательные меры: 

1. TLS 1.2/1.3
- Запретить HTTP;
- Выполнять автоматический redirect с HTTP на HTTPS только для вспомогательных веб-интерфейсов;
- API должен изначально использовать HTTPS.
- Отключить устаревшие протоколы и слабые cipher suites.

2. Проверка сертификата сервера:

- Мобильное приложение должно проверять сертификат сервера.
- Для повышенной защиты мобильного приложения возможно применение certificate pinning, особенно для критичных API.
- 
3. Шифрование всех внутренних интеграций
- Защищённым должен быть не только канал:
Mobile App → API Gateway
но и:
API Gateway → сервисы

Policy Service → 1С

API → Расписание

API → CRM

API → Платёжный шлюз

LIS → интеграционный контур

4. Защита медицинских и персональных данных

- Не передавать медицинские данные через незашифрованные каналы.
- Не помещать персональные и медицинские данные в URL/query parameters без необходимости.
- Не записывать access token, медицинские данные и платёжные реквизиты в обычные application logs.

5. Минимизация данных
   
API должно возвращать мобильному приложению только необходимые для конкретной операции данные.
Например, для списка записей пациенту не следует передавать внутренние технические идентификаторы, служебные поля CRM и другие данные, которые приложению не нужны.

6. Защита от MITM

- Проверка цепочки сертификатов.
- Для критичных API — certificate pinning.
- Контроль доверенных CA.
  
7. Защита внутренних сервисов
- Межсервисные вызовы должны проходить через аутентифицированные каналы. Для критичных внутренних соединений рекомендуется использовать mTLS, чтобы сервисы взаимно проверяли сертификаты.
  
8. Защита API Gateway
- API Gateway должен выполнять:
- JWT validation;
- Rate Limiting;
- WAF-защиту;
- контроль размера запроса;
- проверку Content-Type;
- корреляцию запросов через X-Request-ID;
- аудит критичных операций.

9. Защита от SQL Injection
Учитывая существующий тикет INT-006, все backend-сервисы должны использовать:
- параметризованные SQL-запросы;
- prepared statements;
- ORM с безопасной параметризацией;
- валидацию входных параметров.
SQL не должен формироваться конкатенацией пользовательского ввода.

10. Защита Alfred
С учётом инцидента SD-007 необходимо исключить доверие к идентификатору пациента, переданному клиентом. Идентичность пользователя должна определяться по валидированному sub из access token, а сервер должен самостоятельно определять, к каким данным имеет доступ данный пользователь.

5. Ключевые архитектурные решения

| Область | Решение |
|---------|---------|
| **Аутентификация** | OAuth 2.0 + OpenID Connect |
| **Flow** | Authorization Code + PKCE |
| **Передача токена** | `Authorization: Bearer <access_token>` |
| **Access Token** | Короткоживущий JWT, например 15 минут |
| **Refresh Token** | Защищённое хранилище ОС устройства |
| **API Security** | API Gateway + JWT validation |
| **Публичный Rate Limit** | 60 req/min/IP |
| **Создание записи** | 10 req/min/user + 2 RPS |
| **Защита от повторной записи** | Idempotency-Key |
| **Внешний транспорт** | HTTPS + TLS 1.2/1.3 |
| **Внутренний транспорт** | HTTPS/mTLS |
| **SQL Injection** | Parameterized queries / prepared statements |
| **Защита сессии** | Идентификация по `sub` из JWT |
| **Защита API** | WAF + Rate Limiting + validation |
| **Медицинские данные** | Шифрование при передаче + минимизация данных + отсутствие чувствительных данных в логах |

Шифрование при передаче + минимизация данных + отсутствие чувствительных данных в логах
Примечание: значения Rate Limiting 60 req/min и 10 req/min + 2 RPS являются стартовыми проектными параметрами. В исходных данных нет фактических RPS и профиля нагрузки мобильного приложения, поэтому окончательные значения следует подтвердить нагрузочным тестированием.
