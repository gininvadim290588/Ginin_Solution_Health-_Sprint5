# Реализация отказоустойчивости интеграции

## 1. Параметры отказоустойчивости

| Параметр | 1С «Полисы» | Платёжный шлюз |
|----------|-------------|----------------|
| **Timeout** | 3 сек | 5 сек |
| **Количество попыток** | 3 всего: 1 основной вызов + 2 retry | 1 попытка проведения платежа; автоматический повтор не выполнять при timeout |
| **Интервал Retry** | 1 сек → 3 сек, с небольшим jitter | Для проверки статуса: 1 сек → 3 сек → 5 сек |
| **Retry при** | Timeout, 502, 503, 504 | Только для безопасного запроса статуса платежа |
| **Retry при бизнес-ошибке** | Нет | Нет |
| **Circuit Breaker** | Обязательно, высокий приоритет | Рекомендуется |
| **Fallback** | Использовать допустимый кэш статуса полиса; при невозможности проверки — `POLICY_CHECK_UNAVAILABLE` | `PAYMENT_PENDING` + асинхронная проверка статуса |
| **Дополнительная защита** | Rate Limit + Concurrency Limit | Idempotency Key + Status Inquiry + Reconciliation |

### Обоснование параметров

**1С — timeout 3 секунды.**  
Из исходных данных известно, что 1С может зависать более чем на 30 секунд. Ожидание 30+ секунд при массовых запросах приведёт к накоплению соединений и рабочих потоков и может вызвать каскадный отказ. Поэтому запрос к 1С должен быстро завершаться по timeout и переходить к ограниченному retry/fallback.

Для 1С используется максимум 3 попытки: первоначальный вызов и два повтора через 1 и 3 секунды. Повторять следует только временные технические ошибки. Небольшой jitter желательно добавить, чтобы одновременно возникшие запросы не создавали повторный пик нагрузки.

**Платёжный шлюз — timeout 5 секунд.**  
Для платежа нельзя использовать агрессивный retry. Таймаут не означает, что платёж не состоялся: деньги могли быть списаны, но ответ не дошёл до «Здоровья+». Поэтому повторять саму операцию списания после timeout нельзя.

Вместо этого выполняется запрос статуса платежа. Если статус ещё неизвестен, платёж переводится в `PAYMENT_PENDING`, а проверка продолжается асинхронно.

## 3. Приоритет Circuit Breaker — 1С

Для 1С «Полисы» **Circuit Breaker является более критичным**, чем для платёжного шлюза.

**Причины:**
- 1С имеет известный предел производительности — проблемы начинаются при нагрузке свыше 50 RPS.
- 1С способна зависать более чем на 30 секунд.
- Retry при уже перегруженной 1С может дополнительно увеличить нагрузку.
- Синхронные зависшие запросы будут занимать connection pool и потоки вызывающего сервиса.
- Отказ 1С может распространиться на API Gateway, BFF и сценарий записи пациента.

Circuit Breaker позволяет быстро прекратить обращения к неисправной системе и локализовать отказ.

Для платёжного шлюза Circuit Breaker тоже полезен, но его основная задача — не допустить лавины запросов. Главный бизнес-риск платежей находится в другой области: неизвестный финансовый результат и потенциальное двойное списание. Поэтому здесь важнее комбинация **Timeout + Idempotency + Status Inquiry + Reconciliation**.

## 4. Механизм работы Circuit Breaker

Используем классическую модель из трёх состояний:
+---------+
| CLOSED |
+----+----+
|
ошибки / timeout
выше порога
|
v
+---------+
| OPEN |
+----+----+
|
cooldown period
|
v
+-------------+
| HALF-OPEN |
+------+------+
|
+----------+----------+
| |
SUCCESS ERROR
| |
v v
CLOSED OPEN

text

### CLOSED
- Нормальный режим.
- Все запросы направляются в 1С, а Circuit Breaker собирает статистику ошибок.

**Предлагаемые стартовые параметры:**
- окно: последние 20 запросов;
- открытие Circuit Breaker: при ≥50% ошибок/timeout, но не менее 5 ошибок;
- время нахождения в OPEN: 30 секунд;
- затем переход в HALF-OPEN;
- в HALF-OPEN: 1–3 пробных запроса;
- успешное восстановление → CLOSED;
- повторная ошибка → OPEN.

> Эти значения являются стартовой конфигурацией и должны быть подтверждены нагрузочным тестированием.

### OPEN
В этом состоянии запросы в 1С не отправляются.

Это предотвращает ситуацию:
1С перегружена
↓
ошибки
↓
Retry
↓
ещё больше запросов
↓
ещё большая перегрузка
↓
полный отказ

text

Circuit Breaker разрывает этот цикл:
1С отказала
↓
Circuit OPEN
↓
запросы к 1С прекращаются
↓
Fallback

text

### HALF-OPEN
Через 30 секунд разрешаются несколько пробных запросов.

- Если 1С восстановилась: `HALF-OPEN → CLOSED`
- Если снова возникают timeout/503: `HALF-OPEN → OPEN`

## 5. Архитектурное решение для снижения нагрузки на 1С

Предлагается выделить отдельный **Policy Service** и разместить перед 1С распределённый кэш **Redis**.

### Целевая схема
Mobile App
|
| HTTPS
v
API Gateway
|
| REST
v
Policy Service
|
+------------------+
| |
v v
Redis Cache 1С: Полисы
^ ^
| |
+------------------+

text

**Policy Service** становится единственной точкой доступа мобильного контура к 1С.

Он отвечает за:
- кэширование результатов;
- timeout;
- retry;
- Circuit Breaker;
- rate limiting;
- concurrency limiting;
- fallback;
- адаптацию HTTP API 1С к внутреннему контракту.

### Как это снижает нагрузку

При каждом запросе:
Mobile App
↓
API Gateway
↓
Policy Service
↓
Redis

text

Если в кэше есть допустимый результат:
Redis HIT
↓
Ответ
1С вообще не вызывается.

text

Только при **Cache MISS**:
Redis MISS
↓
Circuit Breaker
↓
1С

text

Таким образом, количество запросов к 1С становится существенно меньше количества запросов мобильного приложения.

8. Почему именно Policy Service + Redis
Прямой вызов:

text
Mobile App
    ↓
API Gateway
    ↓
1С
создал бы сильную связанность мобильного приложения с Legacy-системой.

При росте пользователей до целевых 50 000 пользователей в часы пик это потенциально создаёт лавину запросов к 1С, которая уже сейчас имеет проблемы при >50 RPS.

Целевой вариант:

text
                         +--> Redis
                         |
Mobile App → API Gateway → Policy Service → 1С
                         |
                         +--> Circuit Breaker
                         +--> Retry
                         +--> Timeout
                         +--> Rate Limit
                         +--> Fallback
изолирует Legacy от внешнего трафика и позволяет централизованно управлять нагрузкой.

9. Итог
Система	Главный риск	Основной механизм защиты
1С «Полисы»	Перегрузка, зависания, каскадный отказ	Circuit Breaker + Cache + Rate/Concurrency Limit + Timeout
Платёжный шлюз	Двойное списание и неизвестный статус платежа	Idempotency + Status Inquiry + Reconciliation + Timeout
Приоритет Circuit Breaker — 1С. Её отказ напрямую способен вызвать каскадную деградацию интеграционного контура, а известный предел >50 RPS делает защиту от повторных и избыточных запросов критически важной.

Для платежного шлюза нельзя решать проблему таймаутов обычным Retry самого платежа. После неопределённого результата необходимо сначала узнать фактический статус операции, а повторное списание разрешать только после подтверждения, что предыдущая операция действительно завершилась неуспешно.

Для разгрузки 1С вводится Policy Service + Redis Cache. Все обращения мобильного приложения к полисам проходят через этот сервис, который централизует отказоустойчивость и не допускает прямого воздействия мобильного трафика на Legacy-систему.

Примечание: значения 3 сек, 5 сек, 2 retry, 1/3 сек, порог Circuit Breaker 50%/20 запросов и 30 сек cooldown — это стартовые проектные параметры. Точные значения необходимо подтвердить нагрузочными тестами, поскольку SLA/внутренние показатели производительности 1С и платёжного провайдера в исходных данных не заданы.
