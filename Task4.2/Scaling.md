# Стратегия горизонтального масштабирования

Для достижения целевой нагрузки **до 50 000 пользователей в часы пик** и времени отклика **< 1 секунды для 99% запросов** наиболее критичными считаю **Расписание** и **CRM**. Именно они участвуют в основных пользовательских сценариях мобильного приложения: просмотр доступных слотов, запись к врачу, получение данных пациента и результатов анализов.

| ИТ-система | Реализация горизонтального масштабирования | Ограничение | Описание решения для него |
|---|---|---|---|
| **Расписание** | Запустить несколько stateless-инстансов сервиса за **Load Balancer/API Gateway**. Состояние пользовательской сессии не хранить на инстансе. PostgreSQL масштабировать через **read replicas** для запросов доступных слотов, а операции бронирования направлять на primary. Для часто запрашиваемых слотов использовать Redis Cache. | **PostgreSQL остаётся узким местом**: операции записи и конкурентное бронирование одного слота требуют согласованности и могут создавать блокировки. | Использовать **read/write splitting**: чтение слотов → read replicas/Redis, бронирование → primary. Для защиты от двойной записи использовать уникальное ограничение на `(doctor_id, slot_id)` и идемпотентный `request_id`. При дальнейшем росте — партиционирование/шардирование по клинике или региону. |
| **CRM** | Запустить несколько экземпляров CRM API за **Load Balancer**. API сделать stateless, а данные сессии вынести из приложения. PostgreSQL масштабировать через **read replicas**, Redis использовать для часто запрашиваемых данных пациента и результатов анализов. Перед CRM использовать API Gateway с rate limiting. | **Единая PostgreSQL БД** ограничивает масштабирование операций записи и может стать bottleneck при росте количества запросов. | Разделить нагрузку на чтение и запись: чтение → replicas/Redis, запись → primary. Для тяжёлых операций использовать асинхронную обработку через брокер сообщений. При дальнейшем росте применить партиционирование данных по региону/клинике и CQRS для наиболее нагруженных сценариев. |
